## Key structural elements (for UI rendering)

When the waiver upload feature ships and the waiver is displayed to users for signature, the UI should:

1. **Render the WARNING header prominently** (uppercase, alert-colored, top of the form)
2. **Require explicit scroll-to-bottom** before the signature field is enabled (prevents users from signing without scrolling through)
3. **Show the current date** at the top of the document (static per-upload or dynamic at signing time)
4. **Capture electronic signature** — typed name + timestamp + IP address + browser fingerprint
5. **For minors**: show Guardian signature fields + relationship dropdown (parent, legal guardian)
6. **After signing**: generate a PDF with the Participant's signature + timestamp rendered into the document, store it in Supabase Storage
7. **Image/likeness consent**: the paragraph at the end is implied consent by signing — no separate checkbox needed per the document text, but consider a visible acknowledgment
8. **Governing law disclosure** should be visible before signing

## Required DB fields (for waiver_signatures table — already exists)

Per the schema probe (Tier 4.1 era), `waiver_signatures` table has columns. When Tier 4.7 runs:
- `waiver_id` — FK to `waivers` (uploaded doc)
- `profile_id` — who signed
- `signed_at` — timestamp
- `signature_text` — the typed name
- `guardian_name` / `guardian_relationship` — populated if Participant is under 18
- `ip_address`, `user_agent` — for legal defense
- `document_version` — which version was shown at signing time
- `pdf_url` — stored signed PDF
- `image_likeness_consent` — implied true by signing per the doc text

## Versioning

When the waiver is updated (legal review, business model change), the uploaded `waivers` row gets a new version. Existing `waiver_signatures` rows retain a reference to the version they signed under. A new waiver version triggers a re-signing flow for existing members.
