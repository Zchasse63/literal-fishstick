# Spike Recommendations -- Meridian

**Date:** 2026-03-20
**Purpose:** Technical unknowns that need prototyping before committing to full implementation.

---

## Spike 1: Stripe Proration Behavior Verification

**Goal:** Confirm that Stripe's native proration engine produces the expected charges for the Meridian upgrade/downgrade scenarios.

**Approach:**
1. Create two Stripe Price objects in sandbox: $120/mo (6-class) and $225/mo (Unlimited)
2. Create a test Customer with a payment method
3. Subscribe to $120/mo plan
4. On day 15 of 30, upgrade to $225/mo using `stripe.subscriptions.update()` with `proration_behavior: 'create_prorations'`
5. Call `stripe.invoices.retrieveUpcoming()` to see the proration preview
6. Verify: prorated credit = $60.00, prorated charge = $112.50, net = $52.50
7. Test downgrade: `subscription_schedule` to change plan at period end

**Time-box:** 3-4 hours

**Success:** Proration amounts match Edge Case 6 formula exactly. Downgrade takes effect at next billing cycle.
**Fail:** Stripe calculates differently (rounding, timing, anchor date behavior). If fail: document actual behavior and adjust Edge Case 6 policy to match Stripe reality.

## Spike 2: Supabase RLS Multi-Role Access Patterns

**Goal:** Verify that a single user with multiple roles (owner + member) can access the correct data through RLS policies without conflicts.

**Approach:**
1. Create a Supabase project with 3-4 representative tables (users, bookings, revenue_transactions, class_slots)
2. Write RLS policies for owner, trainer, and member roles
3. Create a test user with both `owner` and `member` roles in JWT custom claims
4. Test: as this user, can they see all studio bookings (owner view) AND their own bookings only (member view)?
5. Test: does the current route context (admin vs. member) correctly select which RLS policy applies?
6. Test: what happens with a Supabase client using a JWT that has multiple roles?

**Time-box:** 4-6 hours

**Success:** RLS policies correctly scope data based on the current UI context. A dual-role user sees admin data in admin routes and member-scoped data in member routes.
**Fail:** RLS cannot distinguish "same user, different context" -- the broadest role always wins. If fail: implement a separate "active_role" claim in the JWT that changes when the user switches context.

## Spike 3: Wallet Offset Payment Flow

**Goal:** Prototype the gift card wallet offset flow where wallet balance is consumed before the Stripe card is charged.

**Approach:**
1. Create a mock `wallet_balances` table in Supabase
2. Given: member has $50 wallet balance, wants to buy a $120 membership
3. Server-side: create a PaymentIntent for $70 (total - wallet balance)
4. Client-side: render Stripe Payment Element for the $70 amount
5. On payment success webhook: atomically debit wallet by $50 and mark order complete
6. Test: what if Stripe charge succeeds but wallet debit fails? (Need rollback or compensation logic)
7. Test: what if wallet covers the full amount? ($0 Stripe charge -- use `stripe.paymentIntents.create({ amount: 0 })` or skip Stripe entirely?)

**Time-box:** 6-8 hours

**Success:** Atomic wallet + Stripe payment flow works with correct rollback on failure. Edge cases (full wallet coverage, partial wallet, zero wallet) all handled.
**Fail:** Atomic cross-system transaction (Supabase + Stripe) is unreliable. If fail: switch to wallet-as-credit model where wallet generates a Stripe coupon/credit applied to the invoice.

## Spike 4: Geofencing Accuracy at Studio Location

**Goal:** Test Web Geolocation API accuracy at The Sauna Guys' studio address to determine the correct geofence radius.

**Approach:**
1. Visit the studio with 3 devices (iPhone, Android, laptop)
2. Open a test page that calls `navigator.geolocation.getCurrentPosition()` with `enableHighAccuracy: true`
3. Record GPS coordinates from each device, 5 readings each
4. Calculate variance from the studio's known coordinates
5. Test at 200m away, 300m away, and 400m away to find the boundary where clock-in should fail

**Time-box:** 2 hours (on-site visit)

**Success:** GPS accuracy is consistently within 50m. 300m radius works reliably with no false rejections at the studio.
**Fail:** GPS accuracy is 100m+ (common indoors). If fail: increase radius to 500m, or use a secondary verification method (studio WiFi SSID detection as supplementary signal).

## Spike 5: QR Code Scanning with iPad Camera

**Goal:** Verify that QR codes generated by the `qrcode` npm package can be reliably scanned by the iPad camera used at the front desk.

**Approach:**
1. Generate QR codes at various sizes (200px, 300px, 400px) using the `qrcode` package
2. Encode a sample signed JWT (the proposed QR token format)
3. Display on an iPhone screen (simulating the member showing their phone)
4. Scan with the front desk iPad's camera
5. Test: minimum QR size that scans reliably at arm's length
6. Test: does the QR scan work through the iPad's browser camera API, or does it need a native camera app?

**Time-box:** 2-3 hours

**Success:** QR codes scan reliably at 300px+ from phone screen to iPad camera at 1-2 foot distance. Browser camera API works.
**Fail:** Browser camera API is unreliable for QR scanning on iPad Safari. If fail: use a JavaScript QR scanning library (e.g., `jsQR` or `html5-qrcode`) that processes the camera feed in the browser, or fall back to manual code entry.
