## Contradiction 1: E2E Auth Files -- Committed vs Not Committed

**project-structure** claims: "There is no `.gitignore` inside `e2e/.auth/` and the root `.gitignore` does not exclude `e2e/.auth/`." (CRIT-002)

**testing-quality** claims: "These files are excluded from git via `apps/web/.gitignore` (line 17: `e2e/.auth/`)" and "`git log --all --full-history -- apps/web/e2e/.auth/admin.json` returned no commits."

**security** claims: "The root `.gitignore` does not exclude `e2e/.auth/`. There is no `.gitignore` inside `e2e/.auth/`."

**Evidence strength**: Testing-quality has the strongest evidence -- it checked both the `.gitignore` and the git history, confirming the files ARE gitignored (via `apps/web/.gitignore`, not root) and were never committed. Project-structure and security checked the root `.gitignore` but missed the workspace-level `.gitignore`.

**Resolution**: Resolved. The files are correctly gitignored at the `apps/web/` level. The root `.gitignore` does not need to duplicate this. The files exist on disk (generated by Playwright auth setup) but are not in version control. The real risk is working-directory exposure, not version-control exposure. Severity should be downgraded from CRITICAL to HIGH -- credential rotation is still recommended as a precaution, but there is no evidence of actual exposure.

**Impact**: Determines whether this is an active credential leak (CRITICAL) or a defense-in-depth gap (HIGH).

**Evidence strength**: Both can be correct simultaneously. The data-model layer audited the API route handler code (which writes wrong column names). **Resolution**: Resolved. The finding is CRITICAL for the write path (creating new classes via the API will produce records with NULL timestamps) and non-issue for the read path (existing classes display correctly). The class creation flow from the admin UI is indeed broken.
